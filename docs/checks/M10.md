## Decisions

1. **Plain `dpkg-deb` script, not cargo-deb.** cargo-deb isn't installed and would be a new tool to install; its asset list would still need a script around it for libghostty, Ghostty resources, PNG icons and the rpath. `scripts/package-deb.sh` is ~100 lines with no new tools. `dpkg-shlibdeps` computes Depends (staged under `debian/rade/` so it accepts the private lib); `libgl1` is added by hand because GLAD `dlopen()`s it.
2. **RUNPATH via a build env, separate target dir.** No patchelf/chrpath on the machine. `crates/rade-app/build.rs` uses `RADE_LIBGHOSTTY_RPATH` (package script: `'$ORIGIN'`) else the absolute `ghostty/zig-out/lib` as before. The package build uses `CARGO_TARGET_DIR=target/deb-build`, so `target/release` (dev, tests, the owner's pre-package launcher) is never relinked. Cost: a second full release build (~40 s here after deps are cached in `target/deb-build`).
3. **Bundle Ghostty resources** under `/usr/share/rade/{ghostty,terminfo}` instead of reusing `/usr/share/ghostty`: shell integration must match the bundled libghostty version, and the package must work without Ghostty. 2.5 MB. The existing ancestor search in `terminal/runtime_env.rs` finds it with no new code; `cargo install` builds get a baked fallback to the clone's `ghostty/zig-out/share/ghostty`.
4. **Keep `GNOTIFICATION_BACKEND=freedesktop` and `NON_UNIQUE`, also when installed.** The gtk/portal backend would need a unique `GApplication` (D-Bus name `dev.rade.App`) for GNOME Shell to call `ActivateAction`. Unique would mean: a second launch forwards to the first and exits; the live harness (a copy of the binary, Installed flavor, its own socket) could no longer run next to the owner's installed RADE; a broken session bus would stop startup. The freedesktop backend already works with the Focus button (owner-verified M3, E2E M3/M6), and GLib sends the app id as the `desktop-entry` hint, which GNOME uses to show the notification under the RADE app (name, icon, per-app notification settings) once `dev.rade.App.desktop` is installed. A second launch hands off to the running app instead (decision 7).
5. **Flavor by binary location, at run time** (ADR-0010): inside a Cargo target dir (`CACHEDIR.TAG` ancestor) = Devel (`dev.rade.App.Devel`, `rade-dev.sock`, `~/.local/share/rade-dev`, "RADE (dev)"), else Installed. Applies to the CLI too: `target/release/rade` outside a Pane talks to the dev app, `/usr/bin/rade` to the installed one; inside Panes `RADE_SOCKET` decides (deviation from the brief's "outside panes = installed socket" for the dev CLI only: otherwise every dev/E2E run would need `RADE_SOCKET`). Config and paste cache are shared. Rejected: `debug_assertions` (dev and tests are release builds), a cargo feature (second build + flag for `cargo install`).
6. **Icon**: own simple SVG (terminal prompt + agent graph), PNG sizes rendered at package time with GdkPixbuf (python3-gi) instead of committing binaries.
7. **Second launch hands off** (review finding, existing bug made easy to hit by a launcher): before GTK starts, `rade-app` connects to its socket; if a RADE answers it asks it to `present` its window and exits 0 without loading/saving state. Desktop file sets `SingleMainWindow=true`.
8. **Version** `<workspace version>+git<commit date>.<short hash>` so every rebuilt package upgrades with `apt install ./…deb`.
9. **No `/usr/bin/rade-app` wrapper script**: a symlink is enough because glibc resolves `$ORIGIN` and `current_exe()` via `/proc/self/exe` (m10 starts the app through the symlink).

## Deviations / limits

- lintian not run (not installed; installing needs root). Expected warnings: no man pages, private `libghostty-internal.so` without SONAME version / shlibs, `Maintainer` placeholder address, the Rust crate licenses as one gzipped text instead of DEP-5 stanzas.
- Deviations from the M10 plan text in MILESTONES.md: no cargo-deb (decision 1), no GNOME `org.gtk.Notifications` route (decision 4); noted there.
- The live harness copies the dev binaries out of `target/`, so its test app runs as the Installed flavor (`dev.rade.App`); it stays isolated by its own `RADE_SOCKET` and XDG dirs (ADR-0010).
- README screenshots come from the E2E (dev) build, so their title reads "RADE (dev)".
- Until the .deb is installed, launching the old `rade.desktop` (→ `target/release/rade-app`, rebuilt in M10) starts the **dev** flavor with an empty `~/.local/share/rade-dev`; the daily state in `~/.local/share/rade` is untouched and comes back with the installed app.

## Owner install steps

```sh
cd ~/workspaces/personal/RADE
scripts/package-deb.sh                                  # if not already built
pkexec apt install ./target/debian/rade_*_amd64.deb
# quit the running RADE (state is saved), then remove the dev launcher + CLI symlink:
rm ~/.local/share/applications/rade.desktop ~/.local/bin/rade
update-desktop-database ~/.local/share/applications 2>/dev/null || true
hash -r; command -v rade                               # → /usr/bin/rade
```

Start **RADE** from the launcher (or `rade-app`). It uses the same paths as before (`~/.local/share/rade/state.json`, `$XDG_RUNTIME_DIR/rade/rade.sock`, `~/.config/rade/config.toml`, Worktrees in `~/.local/share/rade/worktrees`), so Projects, Tabs and Agents restore. `rade setup` re-run is **not** needed: hook commands call plain `rade` (unchanged), which inside RADE Panes resolves to `/usr/lib/rade/rade`. Re-run it only to refresh the installed skill text. Owner checks after install: a desktop notification appears under "RADE" with its icon and its Focus button lands on the Pane; `infocmp xterm-ghostty` in a Pane.

Development afterwards: `target/release/rade-app` opens "RADE (dev)" next to the daily app; use `target/release/rade …` (or `RADE_SOCKET`) to drive it.

# R6 checks — Shift+Enter newline

PRD R6: Shift+Enter inserts a newline (not submit) in Claude Code, Codex, Antigravity CLI and OpenCode, via the kitty keyboard protocol; a Preset may declare a fallback byte sequence. AC: a manual check per Agent Preset, recorded here.

## What RADE does

- RADE never intercepts Shift+Enter in GTK (R16.5). The window's capture-phase key handler (`keys.rs`) matches only configured bindings with exact modifiers; no default is Shift+Enter or plain Ctrl+<key>. Unit tests: `keys::tests::shift_enter_and_ctrl_v_reach_the_terminal` (the default keymap returns no action for Shift+Return, Shift+KP_Enter, Ctrl+V, Ctrl+Shift+V), `config::tests::r17_3_defaults_never_plain_ctrl_or_shift_enter`.
- The key then goes to Ghostty unchanged. Ghostty encodes it per the kitty keyboard protocol once the program has enabled it (`CSI 13;2u`), otherwise as a plain `\r`.

## Decision: no fallback bytes in v1

The Preset field `shift_enter` (R6.2 fallback) is parsed and overridable but **not applied**. Reasons (docs/research/agent-integration.md):

| Agent | Shift+Enter in Ghostty |
|---|---|
| Claude Code | Works with no setup (Claude Code's terminal docs list Ghostty as native) |
| Codex | Composer binds Shift+Enter to `insert_newline`; the TUI pushes kitty keyboard flags |
| OpenCode | `input_newline` includes `shift+return`; Ghostty sends CSI u natively |
| Antigravity CLI (`agy`) | **UNVERIFIED** (not in the research). Its predecessor Gemini CLI enabled the kitty protocol and bound Shift+Enter to `input.newline`; the manual row below decides |

The four built-ins default to `shift_enter = None`. Applying a fallback would also need "has this program enabled the kitty protocol?", which the Ghostty embedding API doesn't expose. Add it only if a row below fails.

## Manual matrix (owner)

In a RADE Terminal, start each Agent, type `line one`, press **Shift+Enter**, type `line two`. Expect: one prompt with two lines and nothing sent yet. Then press **Enter** to send. Also check that **Ctrl+J** still adds a newline.

| Agent Preset | How started | Shift+Enter → newline | Enter submits | Result |
|---|---|---|---|---|
| `claude` | `rade spawn --agent claude` (owner Preset = the `clw` command) | PASS | PASS | LIVE PASS |
| `claude` via alias | `clw` typed in a shell Pane (`CLAUDE_CONFIG_DIR=~/.claude-work claude --dangerously-skip-permissions`) | PASS | PASS | LIVE PASS |
| `codex` | `rade spawn --agent codex` | PASS | PASS | LIVE PASS |
| `agy` | `rade spawn --agent agy` | PASS | PASS | LIVE PASS |
| `opencode` | `rade spawn --agent opencode` | PASS | n/a (no funds) | LIVE PASS (newline); Enter N/A |

If a row fails, note what happened (e.g. the prompt was sent). The fallback (`[agents.<name>] shift_enter = "\u001b\r"`, sent on Shift+Enter for that Preset's Panes) is then implemented; until then the field has no effect.

Live run 2026-10-01 (`tests/live/m5.sh`, real keys via ydotool): typed `say PONG`, **Shift+Enter**, `only that`, **Ctrl+J**, `no more` → three consecutive lines in the Agent's input and no reply; **Enter** → the Agent replies PONG. The `clw` row was typed in a zsh shell Pane; with the file tree shown the Pane loses keyboard focus when Claude registers (bug, docs/checks/M4.md "Live results"), so the harness re-focuses it (`rade focus`) before typing.

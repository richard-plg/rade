## Decisions

1. **Review is a Pane kind** (`PaneKind::Review { root }`), not a Tab or window: it opens split right of the active Tab's focused Pane, so the Agent stays visible next to its diff (the requirement), is reused per Tab, restores like a Viewer and needs no new layout concept. *Trade-off:* a narrow split shows a compact file list above the diff instead of a side-by-side tree; the user can Zoom it (`Ctrl+Shift+Z`).
2. **What the diff includes** (same as Orca's "since base" view): merge-base of `HEAD` with the Project's main branch (`origin/HEAD`'s target, else `main`, else `master`) → working tree: branch commits, staged, unstaged, untracked non-ignored files (status `U`); not ignored files, submodule contents, binary contents. No main branch → `HEAD` (uncommitted only); unborn → everything. Untracked files are included by marking them intent-to-add in a **throwaway copy of the index** (`GIT_INDEX_FILE`), so one `git diff` gives uniform hunks and the Agent's real index is never written (and `GIT_OPTIONAL_LOCKS=0` everywhere). *Trade-off:* copying the index per refresh (a few MB on huge repos); the alternative `git diff --no-index` per untracked file spawns N processes.
3. **Rendering**: one GtkSourceView per Review for the selected file only (natural virtualization), the file's own language highlighting (GtkSourceView's `diff` language would colour whole lines but lose code highlighting), translucent green/red paragraph backgrounds readable on both schemes, two `GutterRendererText`s filled from `query-data` (old/new numbers, sign or ● for a commented line) — no GObject subclassing. Hunks fold via an invisible tag; rows per file capped at 5,000; the patch read capped at 20 MB (title says "diff truncated"). *Trade-off:* removed lines interleaved with added ones can confuse multi-line highlighting (strings/comments); acceptable for review.
4. **Refresh = poll every 3 s while the Pane is mapped**, re-render only when the parsed diff changed (`ponytail:` note in code). A recursive file monitor on a whole Worktree (node_modules, target/) costs more watches than a `git diff` every 3 s; no refresh while a comment is being typed.
5. **Git via the `git` CLI**, not libgit2: worktree support, merge-base, rename detection and the user's git config/hooks behave exactly like the user's git; no C dependency; errors carry git's own message. Always C locale, no prompts, optional locks off. *Trade-off:* process spawns (~ms each) and parsing text output (porcelain/`-z` formats are stable).
6. **`setup` lives in `config.toml`** (`[projects.<id or name>] setup = "…"`), not in `state.json` nor a repo file: config is the user-edited, live-reloaded place (R17.1 already lists Project defaults); state is machine-written. *Trade-off:* not shared with teammates (Conductor/Superset keep scripts in the repo) — an in-repo file can be added later without breaking this. It runs once per Worktree: the pending command is stored on the Worktree (survives a restart before any Terminal opened) and moved to the first Terminal as a transient field (never re-run on restore). Shell Terminals get it typed into the user's own shell (keeps shell integration); Agent/`--cmd` Terminals run it behind a small `sh` wrapper that prints the outcome and starts the Agent either way (a broken setup should be visible, not block the Agent).
7. **Existing branch → checkout, not an error**; the dialog says so and disables the base. `--base` with an existing branch is an error (ambiguous intent).
8. **External worktrees are auto-imported** (start, Project add, `worktree list`), named after their branch; RADE never moves them. Removing one from RADE runs `git worktree remove` like any other. *Trade-off:* no way to hide one; not needed yet.
9. **Remove order**: all checks (dirty, lock, submodules) → close Panes (state saved) → `git worktree remove` → model → branch. A late git failure leaves the Worktree without Panes rather than Panes in a deleted folder. Locked worktrees are never force-removed (a lock is an explicit user statement). Branch deletion failure is a warning, not an error (the Worktree is already gone).
10. **Review Comments anchor to new-file lines**; a comment on removed lines anchors to the new line that follows them and quotes them with `-`. The prompt quotes at most 12 lines per comment. Comments are cleared after sending (the Agent has them); `rade review list` shows the exact prompt before.
11. **No ADR**: none of these is hard to reverse (all behind `rade-core` functions and the API), so they live here, in PRD R12/R13 and API.md.

## Known limits

- The Review shows one file at a time (no all-files scroll); large diffs are truncated, not virtualized line-by-line.
- Hunk folding is per session (not saved).
- Comments are not re-anchored when the file changes after they were written (their `path:line` and quote are as written).
- The New/Remove Worktree dialogs and the Send chooser/Preset dialogs are exercised live only for "New" (keyboard) and single-Agent Send; the others are covered by the CLI paths they share.
- `debug screenshot` does not capture libadwaita dialogs.

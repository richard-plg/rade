# A Task's verify command runs only from trusted config, in its own session

Status: accepted 2026-10-03 (M22, PRD R63–R66); amended by ADR-0025 (M23): every verify command now also needs the owner's confirmation of its exact text in the UI, which replaces the accepted risk on `project.toml` / `workspace.toml` below. Builds on ADR-0017 (layered config, content trust of `.rade.toml`), ADR-0018 (Tasks are files), ADR-0020 (Batch scheduler) and ADR-0023 (`## Verify` is text RADE never runs).

Superseded by ADR-0033 (1.0.0).

M22 makes a Task Run *verified*: when the Task Agent says it is done, RADE runs one deterministic check before the Task reaches `review` (docs/research/ai-native-sdlc.md §3.3, roadmap § M22). That check is a shell command run with the owner's rights, so where it may come from is a security decision.

## Decision

1. **Source of the command.** Only `[task] verify` of the Config Layers of each Task Worktree's own Source in the Task's Project (each Worktree runs its Source's command; the Worktrees are the model's — the Run Tab's branch, Sources of the Project — never the file's `sources:` / `branch:`, which an Agent can edit; acceptance H1). A verify is *required* when any Source of the Project has one; if it then can't run (no such Task Worktree) the Task goes to review flagged `verify failed … can't run it`, never a silent pass. Layers: the user's `config.toml`, the Workspace's `workspace.toml`, the Project's `project.toml`, or the Source's `.rade.toml` **only while trusted** (`rade config trust`, exact content, R29.4). The `.rade.toml` read is the Source's **main checkout**, never a Task Worktree's copy (an Agent can commit one on its branch). Never the Task file (its `## Verify`, any frontmatter key, the Log): Agents write Task files. `rade task verify` uses the same rule; there is no `--command`.
2. **How it runs.** `sh -c <command>` in each Task Worktree in turn (the Worktrees named by the Task's `branch` in its Project), with the app's environment plus the Workspace `[env]` (R23.3), stdin `/dev/null`, its own session (`setsid`: no terminal, its own process group). After `[task] verify_timeout` (default 600 s) the whole session is killed (`killpg` plus every process of the session from `/proc`, which also catches jobs that made their own process group); when it ends, whatever it left running in its session is killed too. A process that leaves the session itself (`setsid`, a daemonizing server) escapes this (acceptance L1; a cgroup would catch it — not done: it runs the same trusted command, so it leaks resources, not trust). Runs off the GTK thread.
3. **Evidence.** All output goes to `<root>/.rade/projects/<p>/verify/T-<n>-<k>.log` (next to `tasks/`, a new `k` per run, `== <source>: $ cmd` / `== exit n after s s` headers), and one Task Log line: `verify passed (`cmd` from project.toml, 12 s, log <path>)` or `verify failed, <what RADE did> (exit 1 in api; …, log <path>)`. The line names the file the command came from, so the owner sees which layer ran. Event Journal: `verify.start` / `verify.end` (`status` passed | failed | timed-out, `secs`, `by` auto | manual), `review.verdict` for M23's flow metrics.
4. **Flow (R64).** Run root `done` while the file says `running` and a trusted verify exists → verify (the live overlay is `verifying`; a Batch item is `verifying`). Pass → `review`. Fail → stays `running`, the Run root gets a prompt with the output's last 40 lines (≤ 4 KB) and the log path; the `[task] verify_rounds`-th failure in a row (default 2) → `review` with `…, n of n, needs review`, and a Batch item fails (it counts for `stop_on`). The failure count and the last result shown in the Task Detail / given to a Reviewer are RADE's own (in memory, reset by a pass or a new start), not read from the Log an Agent can write; after a restart only a Log line whose log file is under the Project's `verify/` counts (acceptance M1). A Run root that is done while a manual verify runs is verified when that one ends (acceptance M3). A result that arrives after the Run moved on (the owner set another status, the Agent works again) is logged and not applied; the next `done` verifies again. `exited` / `error` and Tasks without a trusted verify behave as before (R37). `rade task verify` runs it on demand and never changes the status.
5. **Reviewer rubric (R65).** The Batch Reviewer and the Fan-out Judge get the `## Done when` items (the Task's; for a Fan-out, its prompt's), the verify result (the Task's last verify line; for a Fan-out, the verify run in each candidate's Worktree before judging) and "flag only correctness and requirement gaps", and answer one `DONE <n>: met|unmet — evidence` line per item, parsed after the prompt's last line and kept on the Batch item (`checks`) and the Task Log. `[task] review_guide` (a file; relative = the Source's main checkout, not the Worktree under review) is appended, cut at 8000 characters.
6. **Restart.** A Batch item that was `verifying` goes back to `running` as restored: its Agent gets the "RADE restarted…" prompt and its next `done` verifies again (acceptance M2). A Task outside a Batch whose verify died with the app stays `running` until its Agent is done again or the owner runs `rade task verify` / sets the status. A verify process running when the app is killed finishes on its own (its session is not tracked across restarts).

## Considered Options

- **Run `## Verify` from the Task file** (the agent's own checks): Agent-chosen commands with the owner's rights outside any Agent sandbox. Rejected (ADR-0023 §5).
- **Read `.rade.toml` from the Task Worktree** (the branch being verified): the Agent controls it. Rejected; the main checkout's trusted copy only.
- **Treat `project.toml` / `workspace.toml` as untrusted too**: they are the owner's own files under the Workspace root, edited by the owner and by RADE (`rade project add`), like `config.toml`; the trust rule exists for files that come from a repository. An Agent able to write there can equally edit `~/.bashrc`; the Log line names the file a command came from so a surprise is visible. Accepted risk, not a boundary RADE can enforce.
- **Count failures from the Log**: survives a restart but the Agent writes the Log (it could reset its rounds). Rejected for an in-memory count; a restart gives at most one extra round.
- **Run verify inside a Terminal Pane** (like a Worktree's `setup`): visible, but it needs a screen to scrape, can't be timed out reliably and leaves a shell behind. Rejected for a background process with a log file the Task Detail links to.
- **A separate `[review] guide` table**: one more layered table for one key. Rejected for `[task] review_guide`.

## Consequences

- With no `[task] verify` nothing changes; existing suites and Tasks behave as in M21.
- A slow check holds a Batch slot (`verifying` is live) and delays `review` by its run time; `verify_timeout` bounds it.
- A Fan-out Judge waits for every candidate's verify (in parallel) before it starts.
- Verify logs accumulate under `.rade/projects/<p>/verify/` (no pruning yet; delete old ones by hand).

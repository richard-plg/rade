## Review findings (Opus, fixed in `3cb49bc`)
1. `schedule.run` and a tick could start two runs at once, and the Pane name (`last_n + 1`) could differ from the Run number → one run at a time (a lock), the number taken first. Check `R137-3 two runs at once`, `R137-2 the Pane's number is its Run's`.
2. A Codex session (reported by a hook) was copied onto its Run only by `show` / `runs` / `resume`; a Pane closed before that lost it → copied at every refresh.
3. The Edit form always sent `cron` / `at`: a `done` Schedule's prompt couldn't be saved, and any save reset `checked` → only changed fields are sent. Check `R136-c a done Schedule's prompt edit`.
4. `schedule on` after an early run of an `at` Schedule left it `done` → cleared while its time is ahead. Unit `r136_c_on_again_after_an_early_run`, e2e `R136-c on again`.
5. A removed and re-added Schedule reused the old Tab and restarted numbering beside old Panes → removal lets go of its Tabs and Panes. Check `R137-7 a re-added Schedule opens its own Tab`.
6. `--link` was looked up in every Workspace → only the Schedule's.
7. Resume of a Run recorded without an account used today's default → no account.
8. The form could reset an explicit account to Default (before the account list loaded, or for agents with no accounts) → sent only when changed.

Also found while checking: an older form's close handler cleared the newer form (Save did nothing) — fixed; the e2e's `wait` waited on the app itself — fixed.

## Decisions

1. **Where the Fan-out Tab lives: the Project's main Worktree, Agents `runs_in` their own Worktrees.** A Tab belongs to one Worktree, and the whole point is seeing all Agents at once, so the Tab sits in the main checkout (where you start and end: it is where the Winner lands) and each Pane records `runs_in` = its Worktree. Everything that asks "which Worktree is this Pane in" for behaviour — cwd, `RADE_WORKTREE*`, `setup`, Ctrl+click root, the Worktree's status dot, Review "Send to Agent", Worktree removal — uses `pane_worktree` / `panes_in`. *Rejected:* a Tab per Worktree (no side-by-side view), a cross-Worktree "virtual" Tab (a model change everywhere). *Trade-off:* a Fan-out Worktree's sidebar row has no Tabs of its own until you open its Diff; the Agents are found in the main Worktree.
2. **Layout: siblings tiled evenly** (`Layout::tiles`: ≤ 3 in a row, then two rows), not the Agent Grid (which is Parent + children). The Judge goes below them (62/38). No auto re-arrange: a Fan-out never gains Agents.
3. **Names.** Id `fanout-<n>` (first `n` free of Fan-outs, Worktrees, branches and folders) or `--name`; Worktrees and branches `<id>-<i>` (PRD's `fanout-<n>-<i>`); Pane labels `<preset>-<i>` (same `i`), so `codex-2` lives in `fanout-1-2`. All Worktrees start from one base commit resolved at start, and sizes/diffs are against it (not the Review Pane's "merge-base with main"), so a `--base` other than main compares fairly.
4. **Winner: squash-stage, never commit; no new ADR.** ADR-0008 keeps commit/push/PR out of the app. PRD R15.4 asks to "merge or check out". A `git merge --no-ff` would need RADE to commit (the Agents usually leave uncommitted work) and would author commits on the user's branch. Prior art: Vibe Kanban and Crystal squash-merge; Codex Cloud's `codex apply` applies the patch to the working tree; Orca/Superset/Conductor go through a GitHub PR merge. RADE does what `codex apply` does, with real three-way merging: the Winner's working tree is snapshotted through a throwaway index into a commit object no ref points at (so the Winner's own index and files are untouched, and uncommitted + untracked work is included), then `git merge --squash` stages it on the current branch. The result is staged, not committed; the printed next step is the `git commit` command. *Keep* is the "check out" alternative: the Winner's Worktree and branch stay, its Agent moves there. *Refusals* before touching anything: detached HEAD, an operation in progress, tracked uncommitted changes (they would mix with the Winner's; untracked files git protects itself), empty result. *Conflicts* are left like git leaves them, listed, with `git reset --merge` as the undo. No ADR: this stays inside ADR-0008 (no commit, push or PR), is behind one method, and is easy to change. *Rejected:* `merge --no-ff` / cherry-pick (RADE commits), `git switch` to the Winner's branch (needs its Worktree removed and its uncommitted work committed first).
5. **Judge default `claude`, made read-only by tools, not by trust.** The owner's `[agents.claude]` override runs `--dangerously-skip-permissions`, so "tell it to be read-only" isn't enough. Claude Code gets `--tools Read,Grep,Glob --strict-mcp-config` (no edit, shell or MCP tool exists, whatever the permission mode) plus `--add-dir` for the diff folder and each candidate's Worktree; Codex drops bypass/sandbox/approval flags from the Preset and runs `--sandbox read-only --ask-for-approval never`; other Presets are only told (`read_only: false` in status). It runs in the main Worktree and needs nothing more: the diffs are in its prompt. `claude` stays the default because the owner's config already logs it into the work account and the review task is small; `[fanout] judge` switches it (the live test used Codex).
6. **Judge prompt: bias mitigations from LLM-as-judge practice.** Candidates are shown by Worktree name, never the Agent's (self-preference), in random order (position bias), with a rubric (correctness and completeness first, then scope, quality, tests; "a longer diff is not better"), reasoning before the verdict, and a fixed ending `RANKING: …` / `WINNER: <name>`. Diffs inline up to 48 KiB in total (one command-line argument is capped at 128 KiB), else read from files. *Not done:* judging twice in both orders, and running tests (projects differ; the Judge may read files but not execute). `ponytail:` add a per-Project `test` command to the comparison when one is configured.
7. **Verdict parsing from the screen**, not a file or socket call (a read-only sandboxed Judge can't reliably write or reach the socket): when its turn ends, RADE reads its Terminal and takes the last `WINNER:` line naming a real Agent (Worktree name or label; markdown, bullets and case ignored). Only the text after the prompt's last line is read, and the template lines hold placeholders, so an echoed prompt (or a candidate planting `WINNER:` in its diff) can't be misread (proven live with Codex, which echoes it). Tried for 5 s, then "Judge gave no verdict" and Judge Again is offered.
8. **Progress survives restart by latching.** Session Restore clears Agent Status (ADR-0005), so each Member keeps `finished` (set by done/error/exited or its Pane closing, cleared by a new turn). No process survives a restart, so restore marks every turn ended: an Agent that was mid-turn resumes its conversation idle (R11.2 never replays prompts) and counts as finished; prompt it again and it reopens. The Judge comes back as a plain shell with its verdict kept (its read-only launch can't be resumed safely).
9. **Group wait**: `rade fanout wait <id> --until done|judged` instead of overloading `rade wait <pane>`, so Pane addressing stays unambiguous.
10. **Comparison: files and +/− per Agent**, computed off the GTK thread every 4 s while the bar is on screen and when an Agent finishes. Test results were left out (no generic test command; cost).
11. **Palette form counts**: a spin button per Preset (0–8, four per row), value `preset=n,…`; default one `claude` + one `codex` when both exist (the PRD's mixed example), else two of the first Preset. Enter in a spin button submits (after applying typed digits).
12. **Discard is a force removal.** Fan-out Worktrees exist to be compared and thrown away, so Discard / Clean Up remove them with `git worktree remove --force` and `git branch -D` after one dialog that says the work is lost (the CLI `discard` is the same explicit command). This differs on purpose from R12.3's Remove Worktree (refuse dirty, second confirmation for `-D`). A refused removal (locked) keeps the Fan-out listed.

## Known limits

- A Fan-out Agent that was mid-turn at a restart resumes idle and counts as finished; send it "continue" (Decision 8). A restored Judge is a plain shell.
- Closing the Fan-out Tab asks to discard; `rade close` on its Panes (or on the Tab's last Pane) still removes the Tab without asking, leaving the Fan-out usable from the CLI (a new Judge gets a Tab of its own).
- The Judge is only told to be read-only for Presets other than claude/codex (`read_only: false`).
- A squash with conflicts keeps the Winner's Worktree on cleanup; resolving is up to the user or an Agent.
- The choose dialog's screenshot in the live run was taken before the dialog was drawn; the dialog itself was proven by `debug window --widget rade-fanout-who` and the Enter that chose.
- The owner's Codex account showed "less than 25% of your weekly limit left" during the live run; M9's live test costs two tiny Codex turns plus one Judge turn.

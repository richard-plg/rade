## Decisions and deviations (recorded)

- Customize Project… starts the Agent in the Workspace's General (its root) and names the Project's file in the prompt, not "in the Project folder": a Pane's cwd is its Worktree's; PRD R30.3 says so.
- `.rade.toml` uses a top-level `setup` (= that Source's `[sources.<id>] setup`) besides the layered tables; it is the only key a repo file needs that it can't name otherwise.
- A Worktree's recorded `base` is also the base of Create PR, except a commit hash (a Fan-out Worktree's base).
- `RADE_PROJECT` is not reused and is scrubbed from the app's own env (a dev RADE launched from an older RADE's Terminal leaked it).
- serde_json keeps insertion order here, so `project.add` takes an explicit `bases` order from the CLI.

### Open items

- The `--hook` invocation recorder (`rade status --hook --agent`) finds the Agent's process by the Preset program of the user `config.toml` only, not the layered config; a lower layer that changes an Agent's program (`command = "wrapper …"`) is recorded as whatever user-file program it finds (or nothing), and Restore re-runs that. Usually the same binary; worth layering in M17.
- A `config.toml` that still has `[projects.*]` is rejected whole at upgrade (defaults used): custom Presets are missing until it is fixed, so their Agents restore as shells (sessions kept; they resume after the fix and a restart). Documented in the CHANGELOG "Removed"; a softer path would be to drop only the old table.
- `rade config trust` does not show the content being trusted, and an Agent in a Pane can run it itself (it can already run any command, so no escalation).
- Trust is checked and the file read in two steps (a change in between applies once); `workspace.toml`/`project.toml` from `workspace setup --from <git-url>` are trusted by that explicit clone (ADR-0017).

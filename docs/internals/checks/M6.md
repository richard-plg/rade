## Decisions

1. **Coalescing rule (R3.1).** Per Pane, a *status* Notification (an Agent Status transition, from a hook or a fallback) and a *message* (OSC 9/777, BEL, `rade notify`) within 5 s of each other, in either order, are one entry. Text: status first, then the message with its OSC title (`perm needs input — Claude Code: Claude needs your permission`); a BEL adds nothing ("Bell" is replaced by the status text); one message per entry, later ones within the window are absorbed (Codex sends two OSC 9 per turn: the reply and the user's own notifier). Two statuses never merge (two events); two messages never merge (only the old 2 s same-text dedupe). The entry keeps its id, read state and panel position; the desktop banner is re-sent with the same GNotification id, which GLib's freedesktop backend turns into `replaces_id` (verified: E2E `REPLACE`, live `notify_calls … replace`). `rade notify --status X "text"` therefore gives one entry. *Trade-offs:* a message is merged into whatever status entry came within 5 s even if unrelated (rare: both would be about the same Pane at the same moment); the merged text can be long (panel rows ellipsize at 2 lines); an already-read entry absorbs a late duplicate silently rather than raising a new unread one (it is the event the user saw). Alternatives rejected: suppressing the Agents' own notifications (needs per-Agent config edits RADE doesn't own), dropping OSC from hooked Panes entirely (loses the useful reply text and OSC from plain shells).
2. **Focus after re-render.** Always re-grab the model's focused Pane unless a text entry holds focus. *Trade-off:* a re-render (any model update: a Notification, a status change) takes focus back from the file tree or a clicked header button — that was already the behavior (the tree never keeps focus for typing, and a focused button would eat Space/Enter). A narrower fix (grab only after a rebuild) would leave the next rebuild-free path exposed to the same GTK deferral.
3. **Back list stores the line the file was opened at**, not the scroll position at the moment of leaving. *Trade-off:* scrolling around then following a link returns to the opened line, not the exact viewport. Keeping the model free of per-scroll writes (and `state.json` churn) was preferred; revisit if it annoys.
4. **Worst-of order:** error > waiting > running > done > exited. `running` outranks `done` because a Tab with one busy and one finished Agent is still busy; `done` is the resting state.
5. **Palette** moved to `rade-core` (`AgentStatus::color`) so the contrast test runs without GTK; darker amber/green than GNOME's defaults were needed for 3:1 on the light sidebar (`#ebebed`).
6. **Tab dot = the `AdwTabPage` icon** (an SVG circle via `gio::BytesIcon`): Tab titles are plain text, the indicator slot is Zoom's.
7. **Fallback rules (R10.2), conservative by construction:** only Agent Panes (a Preset; `--cmd` programs and shells never get a status — a `--cmd` program is not an Agent in CONTEXT.md terms), only from `running`, never within 10 s of a hook report, only for a status the Pane's hooks can't report; a Preset whose hooks never reported counts as hookless, a status a hook did report counts as reportable even if the Preset declares no hook for it. Signals: OSC/bell → `waiting`; screen unchanged for `idle_seconds` (reused from `rade wait --until idle`, default 5) → `done`, or `waiting` when a done hook exists (agy); OSC 133 command-finished in a shell Pane with a hand-started Agent → `exited` (not a guess: the process is gone; no grace). Not used: titles and OSC 9;4 progress (research §6). A Codex Preset's OSC 9 means `done` (its only OSC 9 is the turn-end reply, research §6), so `rade wait --until done` returns for untrusted Codex. *Trade-offs:* an untrusted Codex's approval request (if it notifies) also reads as `done` — both mean "your turn", and the R16.4 hint tells the user to trust the hooks; a hookless Agent's status follows only turns RADE sees start (spawn, `send --enter`) — inferring `running` from screen changes was rejected because typing into the prompt changes the screen too and would flip the status (and raise "finished") on every keystroke burst; Ctrl+Z on a hand-started Agent reads as `exited` (OSC 133 fires) and its Pane is restored as a shell; idle can misfire for an Agent that computes silently without a spinner for > `idle_seconds` (none of the four built-ins does); the idle watcher reads the screen of running Agent Panes once a second (only those, to keep R4's idle CPU).
8. **`status_source` values** are `hook` and `heuristic` as asked; `hook` also covers what RADE knows for certain (spawn with a prompt, `send --enter`, process exit). A third value was not worth an API change.
9. **Codex hint condition:** a turn RADE saw start (spawn with a prompt or `send --enter`) running ≥ 30 s with no hook report since it began. With trusted hooks `UserPromptSubmit` reports at once; the legacy `notify` (no trust gate) only reports at turn end, so "never reported" alone would miss untrusted hooks after the first turn. Prompts typed by hand into Codex are not seen (RADE doesn't know a turn started) — accepted. Shown as an `AdwBanner` (dismissable, once per app run) rather than a toast (needs no overlay, stays until dismissed).
10. **Exited hand-started Agent on restore:** the Pane loses its Preset, session and invocation, so it is restored as a shell now and on every later restart; the Agent's next session-start report (`clw` again) makes it an Agent Pane again.
11. **No ADR:** none of these is hard to reverse or architecture-shaping; the behavior is in PRD R3.1/R10.2/R10.3/R16.4 and these notes.
